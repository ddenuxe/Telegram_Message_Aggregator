# TG Monitor 1.2.22

Загрузка истории ускорена там, где процессор сервера свободен. Раньше страницы истории
всех аккаунтов читались не более чем в два потока. Теперь число потоков подстраивается
под загрузку процессора: начинается с прежних двух, каждые 5 секунд добавляется ещё
один, пока весь сервер загружен меньше чем на 45%, — до восьми; выше 55% потоки
убавляются, при 60% фоновая работа, как и раньше, ставится на паузу. Ограничения
Telegram действуют на каждый аккаунт отдельно, поэтому выигрыш получается за счёт того,
что одновременно загружается больше аккаунтов. В модели с 11 аккаунтами и свободным
процессором за то же время загружено в 3 раза больше сообщений; реальный выигрыш
зависит от процессора сервера и ответов Telegram. Приём новых сообщений эти
ограничения не затрагивают. Текущее число потоков видно в `/api/health`
(`history_slots`).

Под шкалами истории каждого аккаунта и общей шкалой показывается скорость загрузки
(сообщений в минуту) и примерное оставшееся время. Скорость считается в браузере по
изменению числа сохранённых сообщений и появляется примерно через 20 секунд.

Поиск сообщений использует индекс SQLite FTS5 и больше не перебирает весь архив при
каждом запросе. На синтетическом архиве из 300 000 сообщений редкое слово находится
примерно за 20 мс вместо 0,7 с, частые слова — за 30–40 мс; отдельные запросы из
частых коротких сочетаний вроде «ра ра ра» занимают до 0,4 с. По индексу регистр букв
не учитывается и для кириллицы: «Привет» находит «привет».

Индекс хранит только поисковые фрагменты, без второй копии текстов. Уже сохранённые
сообщения добавляются в индекс в фоне порциями по 500 с тем же регулятором CPU, что и
история; на 300 000 сообщений это около 10 секунд работы базы, растянутых паузами.
До завершения, а также для запросов из двух символов, поиск работает прежним
способом и с прежним поведением (регистр русских букв учитывается). Новые, изменённые
и удалённые сообщения попадают в индекс сразу.

Цена индекса: запись сообщений дороже — порция истории из 200 сообщений в замерах
стала примерно на 15% медленнее в среднем; слияние частей индекса вынесено в фон,
чтобы не создавать долгих пауз при записи. База вырастает примерно на 20–50% объёма
текстов (на сервере с 1,4 млн сообщений ожидается порядка 100–150 МБ).

`run.log` больше не растёт бесконечно: при 10 МБ журнал переносится в `run.log.1`,
хранятся три прежние копии. Старый большой журнал переносится при первом запуске.
Ошибка записи журнала никогда не прерывает работу программы.

Вход в панель: пароль с русскими буквами больше не вызывает ошибку сервера, а
некорректный запрос входа получает отказ вместо ошибки 500. Cookie входа теперь
подписана случайным ключом установки (`panel-secret.key` в папке данных): по
украденной cookie нельзя подбирать пароль, а смена пароля завершает все входы.
После обновления браузеры, где был выполнен вход по паролю панели, попросят пароль
один раз. Basic Auth сайта это не затрагивает.

Если Telegram не отвечает при остановке или очистке, файл сессии всё равно
закрывается, и Windows не держит его заблокированным.

Для сопровождения: версия задаётся одной константой `APP_VERSION` в `app.py`;
`verify_bundle.py` сверяет сборку с ней. `scripts/release_tools.py` разбивает ZIP
на части для передачи и создаёт updater следующей версии из предыдущего, меняя только
версии и контрольные суммы.

Изменения базы только добавляют таблицы `messages_fts`, `search_index_state` и
триггеры. Существующие сообщения, сессии, медиа и настройки не меняются.

Установщик сервера принимает только 1.2.21 и перед остановкой программы проверяет
свободное место на диске (размер базы × 1,35 + 2 ГБ: резервная копия и рост индекса).
На крупном архиве база вырастет пропорционально объёму текстов.

Проверки: 208 тестов Python и 20 тестов JavaScript на Windows/Python 3.14, независимая
проверка изменений с экспериментом на синтетическом архиве из 1,4 млн сообщений.
Собранный EXE прошёл `verify_bundle.py` и проверку обновления: архив, созданный 1.2.21,
открыт 1.2.22 без изменения сохранённых сообщений, индекс построен, поиск работает.
